# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Danica Dynamic Campaign (DCC): a perpetual, persistent dynamic campaign for DCS World. One Lua 5.1 engine
runs inside a 24/7 server mission; the war ticks on whether anyone is online, saves to
`Saved Games\DCS\DCC\<Map>_war.json`, and when one side wins (conquest or the war clock) a server hook loads
the next map (Caucasus → Syria → Persian Gulf → Cold War Germany). README.md is the full player/server manual;
its "How it works (the concepts)" table defines the vocabulary (node, edge, platoon, tick, supply, live bubble,
read-back, mission board, contact, theater pack, era catalog…).

## Configuration: all numbers live in `src/dcc_config.lua`

Every tunable number is in `src/dcc_config.lua` (`DCC.config`), each with a comment. Engine code reads them via
`self.cfg.<section>.<key>` (model) or `DCC.config` — do not hard-code numbers in `src/`. When adding a feature,
add its settings to the matching section there (e.g. `ext4.mines`, `ext4.bogey`) and, if it matters to server
admins, to the Tuning table in README.md. Exceptions: per-map balance is `balance` in the theater pack, and
aircraft stock per base is `aircraftStock` in the catalog.

`DCC.config.version` is the project version; it must match the top entry in CHANGELOG.md.

## Commands

Everything runs offline under Python with `lupa` (bundled Lua 5.1, the version DCS uses). No DCS needed.
Use the repo's virtualenv in `.venv/` (git-ignored); activate it first (`source .venv/bin/activate`) or call
`.venv/bin/python` directly. If it is missing: `python3 -m venv .venv`.

```bash
pip install lupa                                  # tests and simulator (installed in .venv)
pip install matplotlib                            # only for plot_war.py
pip install git+https://github.com/pydcs/dcs.git  # only for make_mission.py

# Run one test suite (each prints ok/FAIL lines and a "N passed, M failed" summary; exit code 1 on failure)
python tools/run_lua.py tests/test_war.lua

# Run all suites
for t in tests/test_*.lua; do python tools/run_lua.py "$t" || echo "FAILED: $t"; done
python tests/test_companion.py                    # web map / Discord companion (Python)

# Offline war simulation and plot
python tools/run_lua.py tools/sim.lua 4320 2026 docs/sim_history.json
DCC_THEATER=Syria python tools/run_lua.py tools/sim.lua 4320
python tools/plot_war.py docs/sim_history.json docs/sim_war.png

# Rebuild the shipped artifacts after changing src/, catalogs/, theaters/ or kneeboard/mission tools
python tools/build_bundle.py                      # -> dist/dcc_bundle.lua
python tools/make_mission.py                      # -> dist/DCC_Caucasus.miz
for m in Syria PersianGulf GermanyCW; do python tools/make_mission.py --theater $m --out dist/DCC_$m.miz; done
python tools/make_mission.py --test               # -> dist/DCC_Caucasus_ArmouryTest.miz
```

There is no single-test filter inside a suite; run the suite file. Bridge tests write temp saves under
`arg[1]` or `/tmp`.

## Architecture

**Spawned units are a view of the saved numbers.** The war is a pure-Lua model; DCS units exist only near
players (the 40 km "live bubble") and are rebuilt from the save at any time. Everywhere else battles run on dice.

Two layers, strictly separated:

- **Pure model** (`src/dcc_war.lua` + `dcc_supply`, `dcc_ops`, `dcc_missions`, `dcc_pilots`, `dcc_intel`,
  `dcc_radar`, `dcc_world`, `dcc_air`, `dcc_ground`, `dcc_ext*.lua`, `dcc_front`, `dcc_territory`): no DCS API
  calls. `dcc_war.lua` defines the `War` class (`DCC.War`, created with `DCC.War.new(theater, catalog, cfg, seed)`,
  stepped with `w:tick()`); every other model file adds methods to that same `War` table (`function War:foo()`),
  so features are spread across files but share one object and one `w.state` (the save).
- **DCS bridge** (`src/dcc_dcs*.lua`): spawning/despawning, 30 s read-back of live groups into the model, F10
  drawing and menus, warehouses, events. They hang off `DCC.dcs`. `dcc_persist.lua` is the only file access;
  `dcc_main.lua` holds `DCC.start()` and the 30 s / 5 min loops.

**Load order matters** and is listed in three places that must be kept in sync when adding a module:
`tools/run_lua.py` (`PURE_MODULES`, model only), `tools/build_bundle.py` (`ENGINE`), and `src/dcc_loader.lua`
(development loader). Bridge test suites also `dofile` the bridge modules in their own list near the "Bridge"
section of each test. Feature files state which file they load after in their header.

**Data, not code, describes maps and eras.** No map is named in engine code: `theaters/*.lua` (nodes with lat/lon,
roads, owners, ships, sea lanes; Caucasus hand-made, others generated by `tools/make_theater.py` from
`tools/scenarios/*.py`) register into `DCC_THEATERS`; `catalogs/modern.lua` maps roles to DCS unit types per side
into `DCC_CATALOGS`. `make_mission.py` reads the same packs, so missions and engine never disagree.

**Tests**: model tests construct a `War` directly and assert on `w.state`; bridge tests load
`tests/dcs_mock.lua` (a flat-projection fake of the DCS scripting API, controlled through the global `MOCK`, e.g.
`MOCK.advance(seconds)`) and then the bridge modules, and count logged `ERROR`s. `tests/ctld_shim.lua` /
`test_ctld.lua` run the real vendored `vendor/ctld/CTLD.lua`. Every mission type has a test that its effect lands
in the save (`tests/test_ops.lua`); new features go into the matching suite (recent ones: `test_ext4.lua`).

Other pieces: `hooks/DCC_rotation_hook.lua` (server hook, reads `DCC\rotation.json` to load the next map),
`server/dcc_companion.py` (web map + Discord from `public.json` / `feed.jsonl`), `tools/kneeboard.py` (kneeboard
pages baked into the .miz), `dtc/` (DTC templates).

## Release conventions

Each change is a version bump: update `version` in `src/dcc_config.lua`, add a CHANGELOG.md entry
(**Added** / **Changed** / **Fixed**), update README.md where behaviour is described, rebuild `dist/` (bundle
and all .miz files are committed), and commit as `vX.Y.Z: <summary>`.

## In-DCS test plan and feedback loop

`docs/dcs-testplan.md` (Danish) lists every check that needs real DCS: `S-` tests need server access, `P-` tests
can be done by a pilot in multiplayer. Each test has a stable ID, a `Status:` line (`IKKE TESTET`, `OK`, `DELVIS`,
`FEJL`, `RETEST`, `SPRUNGET OVER`), a `Feedback:` field and the offline suite that covers it.

- A new feature gets a new test there in the same commit; a changed feature sets its tests to `RETEST`. Never
  renumber IDs; new tests take the next free number in their area.
- When the user says they have tested: read every `FEJL` / `DELVIS` test and its feedback, first reproduce the
  problem as a failing check in the named offline suite, then fix, run all suites, do the release steps above, set
  the test to `RETEST` and add a `Rettet i vX.Y.Z: …` line under its feedback.
- Keep the *Røgtest* list current: it is the set the user runs after every release.
